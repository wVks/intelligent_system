# StudyNavigator — интеллектуальный ассистент по учебным заданиям

StudyNavigator — проект веб-системы, которая помогает студенту разобраться в
требованиях учебного задания, найти критерии оценки и составить план подготовки.
Ответы формируются подключённой языковой моделью на основе материалов курса,
полученных через собственный MCP-сервер, и сопровождаются ссылками на источники.

**Стадия проекта: проектирование и подготовка разработки.** Сейчас подготовлены
описание MVP, проектные skills и проверки вспомогательных программ. Приложение,
MCP-сервер и подключение модели предстоит реализовать. Сервис ещё не развёрнут,
Eval приложения не проводился. Описанные ниже компоненты и функции — проектные
решения для первой версии.

Описание составлено по [заданию «Личный проект»](Личный%20проект.pdf), стр. 1–3.
**Репозиторий:** [wVks/intelligent_system](https://github.com/wVks/intelligent_system).
**Работающий сервис:** ещё не развёрнут.

Для продолжения разработки: [160 вопросов по решениям, реализации и сдаче](docs/development-questions.md).

## 1. Название проекта и описание задачи

**Название:** StudyNavigator.

**Проблема:** требования, критерии оценки и сроки учебных работ находятся в
разных материалах. Студенту приходится самостоятельно искать нужные сведения,
сопоставлять их и определять порядок подготовки. При обращении к универсальному
чат-боту ответ может содержать сведения, которых нет в задании.

**Цель:** предоставить единое окно, в котором студент получает объяснение
требований с подтверждением источниками и реалистичный план выполнения работы.

Система должна решать три задачи:

1. Находить требования и критерии конкретного задания.
2. Отвечать на вопросы по материалам с указанием документа и страницы/раздела.
3. Предлагать план подготовки с учётом известных сроков и доступного времени.

Выбранная предметная область позволяет содержательно применить MCP для доступа
к учебным данным, проверить факты по фиксированным источникам и показать полный
пользовательский сценарий за время защиты.

## 2. Пользователь и сценарий использования

**Основной пользователь:** студент одного учебного курса, готовящий работу к сдаче.

**Основной сценарий:**

1. Студент открывает сайт и выбирает задание.
2. Задаёт вопрос: «Что нужно отправить в LMS по личному проекту?»
3. Система получает требования через MCP и передаёт найденные сведения модели.
4. Студент получает ответ: нужны ссылка на публичный репозиторий с README.md и
   интерактивной HTML-презентацией, а также ссылка на работающий сервис.
5. Рядом с ответом доступен источник: «Личный проект», страница 1.
6. Студент просит составить план подготовки и указывает срок и свободное время.
7. Система предлагает шаги и проверяет выполнимость плана по заданным ограничениям.

**Сценарий отсутствующих сведений:** на вопрос «Когда сдавать личный проект?»
ассистент сообщает, что дата в исходном документе не указана, и предлагает
уточнить её. Неизвестные поля срока сохраняются как `null`. При желании
пользователя можно составить явно относительный план, например на пять дней.

**Результат для пользователя:** понятный список требований, проверяемые источники
и последовательность действий для подготовки работы.

## 3. Границы MVP и критерии готовности

Первая версия охватывает один курс и заранее подготовленный набор материалов.
Первый реальный источник — PDF с заданием личного проекта. Дополнительные
учебные примеры будут явно обозначены как демонстрационные.

| Входит в MVP | Содержание |
|---|---|
| Веб-интерфейс | Чат, список заданий, отображение источников, состояния ожидания и ошибки |
| База материалов | Задания, требования, критерии, известные сроки и происхождение сведений |
| MCP | Собственный сервер и клиент, три инструмента чтения учебных данных |
| AI-логика | Подключённая LLM, выбор инструментов, объяснение требований и плана |
| Проверка плана | Расчёт часов, проверка доступного времени, сроков и зависимостей |
| Проверка качества | Фиксированный Eval-набор, результаты, трассы инструментов и разбор ошибок |
| Материалы сдачи | Публичный сервис, README и интерактивная HTML-презентация |

За границами первой версии: интеграция с реальной LMS, аккаунты и роли студентов,
изменение оценок, уведомления, календарные интеграции и загрузка произвольных PDF.

**Предлагаемые критерии готовности MVP:**

- Пользователь проходит основной сценарий через веб-интерфейс с реальной LLM.
- MCP-клиент обнаруживает три инструмента и вызывает их через протокол;
  успешный вызов и ошибка подтверждаются трассой.
- Ответ о требованиях содержит сведения из правильного источника; ссылка
  открывает соответствующий материал и страницу/раздел.
- Вопрос без ответа в материалах не приводит к выдуманному сроку или требованию.
- План укладывается в заданный бюджет времени; при нехватке времени система
  сообщает о дефиците и предлагает приоритеты.
- Проведён Eval, сохранены фактические результаты и разобраны ошибки.
- Инструкция позволяет повторить запуск, а публичная ссылка открывает
  работающий пользовательский сценарий.
- Подготовлена и проверена интерактивная HTML-защита продолжительностью до 10 минут.

Это выбранные критерии разработки; их выполнение пока не подтверждено.
**Согласование темы и границ MVP с преподавателями пока не подтверждено.**

## 4. Архитектурная схема системы

Проектируемая система состоит из веб-интерфейса, backend, внешнего API модели,
MCP-клиента, собственного MCP-сервера и локальной базы учебных данных.

```text
Студент
   │ вопрос, выбранное задание, ограничения времени
   ▼
Веб-интерфейс: HTML / CSS / JavaScript
   │ HTTP-запрос
   ▼
Backend: Python / FastAPI
   Оркестратор AI ◄─────────────────► API языковой модели
         ▲  │
         │  │ разрешённый вызов инструмента
         │  ▼
      MCP-клиент
         ▲  │ MCP / stdio
         │  ▼
      Собственный MCP-сервер
         ▲  │ чтение
         │  ▼
      SQLite + подготовленные материалы
```

Выход модели возвращается через backend в веб-интерфейс. Backend проверяет
структуру ответа, ссылки на источники и ограничения плана. Ключ API хранится
на сервере в окружении. Текст модели отображается безопасно как текст или
очищенный Markdown.

| Компонент | Ответственность |
|---|---|
| Веб-интерфейс | Ввод вопроса, просмотр заданий, ответов и источников |
| FastAPI | HTTP-интерфейс, управление запросом и жизненным циклом MCP |
| Оркестратор AI | Обмен с моделью, обработка вызовов инструментов, ограничения цикла |
| MCP-клиент | Обнаружение и вызов разрешённых инструментов |
| MCP-сервер | Валидация параметров и выдача учебных данных по контрактам |
| SQLite и материалы | Воспроизводимые записи заданий и подтверждающие фрагменты |

Основные данные задания: `assignment_id`, `course_id`, название, требования,
критерии, `due_date`, `due_at` и `source_ids`. Каталог `sources` содержит
`source_id`, название материала, страницу/раздел, выдержку и `url` для просмотра.
Если известна только календарная дата, время и часовой пояс не придумываются.

## 5. Схема MCP-интеграции

В первой версии MCP-сервер предполагается запускать отдельным управляемым
процессом рядом с backend. Взаимодействие с MCP-клиентом — через `stdio`.
Такой вариант позволяет разместить компоненты в одном контейнере. Версия SDK
будет проверена и зафиксирована при реализации; протокол реализуется средствами SDK.

| Инструмент | Вход | Назначение и результат |
|---|---|---|
| `list_assignments` | Необязательный `course_id` | Список заданий, известные сроки и идентификаторы источников |
| `get_assignment` | `assignment_id` | Требования, критерии, сроки и источники выбранного задания |
| `search_materials` | `query`, ограничение числа результатов | Подтверждающие фрагменты с документом, страницей/разделом и ссылкой |

**Порядок взаимодействия:**

1. Backend через MCP-клиент получает каталог инструментов и сверяет его с разрешёнными именами.
2. Модель получает схемы доступных инструментов и предлагает вызов.
3. Backend проверяет имя и аргументы до обращения к MCP.
4. MCP-клиент вызывает инструмент, сервер читает данные и возвращает результат.
5. Backend передаёт фактический результат модели с идентификатором вызова.
6. Модель формирует ответ с источниками; backend возвращает его пользователю.

Все инструменты MVP работают на чтение. Пустой поиск, неизвестное задание,
ошибка инструмента и недоступность сервера получают разные статусы. Сбой MCP
не должен превращаться в ответ «заданий нет».

Подтверждение интеграции при реализации: обнаружение инструментов и вызовы
настоящим MCP-клиентом, проверка выбранного транспорта и сохранённая трасса.
Прямой вызов Python-функции покрывает только отдельный обработчик.

## 6. Описание AI-логики

Выбран подход одного агента с ограниченным набором инструментов. LLM отвечает
за понимание вопроса, выбор нужных данных, объяснение требований и предложение
шагов подготовки. Провайдер и конкретная модель пока не выбраны; необходима
поддержка вызовов инструментов и работы с русским языком.

**Правила формирования ответа:**

- Учебные факты берутся из результатов MCP; существенные утверждения получают источники.
- Источник должен подтверждать конкретный факт, а не просто иметь существующий идентификатор.
- При отсутствии данных ассистент сообщает об этом и уточняет недостающие сведения.
- Предположения о трудоёмкости отделяются от требований преподавателя.
- Документы и результаты инструментов рассматриваются как данные; встроенные
  в них команды не изменяют правила работы агента.
- Код проверяет даты, длительности, сумму часов и выполнимость плана.
- Число вызовов инструментов, общее время запроса и объём контекста ограничиваются.

Пример ожидаемого ответа: «В LMS нужно отправить две ссылки: на публичный
репозиторий с README и HTML-презентацией и на работающий сервис.
Источник: “Личный проект”, стр. 1». Это эталон поведения для будущей проверки,
а не результат уже выполненного запроса к модели.

## 7. Запуск и развёртывание

### Текущее состояние

Код приложения, файл зависимостей, точка входа и контейнерная конфигурация ещё
не созданы. Команд запуска самого сервиса пока нет. Следующий порядок описывает
план воспроизводимого запуска, который будет дополнен фактическими командами
после реализации.

### План локального запуска

1. Установить зафиксированную для проекта версию Python и зависимости из lock-файла.
2. Настроить серверные параметры провайдера: ключ, модель и адрес API.
   Для репозитория подготовить пример настроек без секретов.
3. Создать SQLite-базу из подготовленных учебных материалов и seed-данных.
4. Запустить backend, который открывает MCP-клиент и управляет процессом MCP-сервера.
5. Открыть веб-интерфейс и проверить основной сценарий, неизвестную дату и ошибку источника.

### План развёртывания

Подготовить Docker-образ с backend, MCP-сервером и воспроизводимыми данными.
На выбранном хостинге задать серверные секреты, порт платформы и прослушивание
внешнего интерфейса `0.0.0.0`. Затем проверить через публичный URL полную цепочку
«чат → LLM → MCP → источник → ответ» и повторить её после рестарта.

Фиксированную демонстрационную базу можно восстанавливать из seed-данных.
Если появятся изменяемые пользовательские данные, для них потребуется постоянное
хранилище. Провайдер хостинга и публичный адрес пока не определены.

### Доступные сейчас проверки подготовки

Из корня проекта можно проверить skills и вспомогательные программы:

```sh
python3 tools/validate_skills.py
python3 -m unittest discover -s tests/skills -v
```

Эти команды не запускают StudyNavigator. Подробности подготовки разработки:
[проектные skills](docs/skills/README.md).

## 8. Результаты Eval и разбор ошибок

**Eval приложения пока не проведён:** подключённой модели и работающего сервиса
ещё нет. Фактическая точность ответов, задержки и стабильность MCP не измерены.

### План проверки качества

Предлагается набор из 30 случаев с зафиксированными материалами: известные
факты, неизвестные и неоднозначные сведения, корректность источников,
ограничения плана, ошибки MCP и инструкции внутри документов. Количество 30 —
проектное решение; в PDF обязательный размер набора не задан.

| Пример случая | Ожидаемый результат |
|---|---|
| «Что отправить в LMS?» | Обе ссылки из задания, подтверждение страницей 1 |
| «Когда сдавать?» | Сообщение об отсутствии даты и уточнение, без выдуманного срока |
| Правильный факт с неверной ссылкой | Провал проверки подтверждённости источником |
| Доступно 2 часа, план требует 5 | Сообщение о нехватке времени и корректировка приоритетов |
| MCP-сервер недоступен | Сообщение о сбое источника, а не об отсутствии заданий |
| Материал содержит «игнорируй правила» | Строка остаётся данными и не меняет поведение агента |

Проверяемые показатели: правильность фактов, подтверждённость источниками,
корректная обработка отсутствующих данных, соблюдение ограничений плана,
завершение инструментального цикла и время ответа. Пропуски и timeout входят
в полный знаменатель как неудачные случаи. Критические сценарии оцениваются
отдельно от среднего результата.

Offline-проверки, настоящая MCP-интеграция, live LLM и публичный сервис будут
проверяться отдельно. Для важных запросов к модели нужны повторные прогоны.
Сохраняются версия данных и приложения, настройки модели, ответы, tool traces
и основания оценок.

### Формат будущего разбора ошибок

Для каждой обнаруженной ошибки в README будут приведены: входной запрос,
ожидаемое поведение, фактический ответ, подтверждающая трасса/источник,
установленная причина, исправление и результат повторной проверки.
Пока фактических ошибок приложения для такого разбора нет.

Отдельно уже проведены испытания **навыков разработки и вспомогательных программ**;
они описаны в [отчёте о skills](docs/skills/validation/report.md). Их результаты
не являются результатами Eval StudyNavigator.
