# StudyNavigator — интеллектуальный ассистент по учебным заданиям

Веб-ассистент по требованиям, критериям оценки и плану подготовки.
Учебные данные поступают через собственный MCP-сервер; ответ открывает источник
и соответствующую страницу исходного PDF.

**Стадия: сервис развёрнут на VPS; этап 6 завершён не полностью.**
Работают загрузка 1–3 текстовых PDF, постраничное извлечение, хранение и поиск,
разделение браузерных сессий, подтверждаемая карточка с происхождением сведений,
план с правкой минут и выполненными задачами, чат и источники через собственный MCP.
Реальные API YandexGPT Pro 5.1 и Alice AI LLM Flash проверены в изолированных
сценариях: **13 генераций, 23,0777 ₽ из согласованных 25 ₽**.
Ограничения качества и сохранённые ошибки — в [отчёте этапа 5](docs/validation/stage-5.md).
Локальный запуск по умолчанию остаётся **offline-деморежимом**. На публичном
сервере явно разделены роли: **YandexGPT Pro 5.1 — чат, Alice AI LLM Flash — анализ**.
HTTPS и бесплатные HTTP-проверки прошли, но новый live-чат по загруженному
заданию приёмку не прошёл. Из отдельного бюджета этапа 6 в 15 ₽ учтено
**13,7011 ₽ за 14 генераций**, остаток **1,2989 ₽**. Консервативный резерв может
отклонить новый запрос раньше исчерпания остатка. Дальнейшие платные проверки
остановлены. Подробности — [отчёт этапа 6](docs/validation/stage-6.md).

**Репозиторий:** [wVks/intelligent_system](https://github.com/wVks/intelligent_system).
**Публичный сервис:** [открыть StudyNavigator](https://studynavigator.136-234-76-207.sslip.io).
**HTML-защита:** [открыть презентацию](https://studynavigator.136-234-76-207.sslip.io/static/defense.html),
[исходный HTML](web/defense.html). Управление в браузере и хронометраж ещё требуют проверки.

## 1. Название проекта и описание задачи

**StudyNavigator** помогает студенту найти обязательные требования работы,
понять критерии оценки и распределить подготовку по доступному времени.
Студент получает проверяемый ответ с документом, страницей и выдержкой.

Студент может загрузить комплект PDF одного задания. Подготовленный пример —
трёхстраничное задание «Личный проект». После загрузки пользователь проверяет
карточку требований и рассчитывает план. В offline карточка заполняется вручную;
в live её предлагает подключённая модель. Автоматический разбор проверен на
реальных API в небольшом пилоте, его известные ошибки сохранены в отчёте.
Отсутствующие сведения сохраняются как неизвестные: система не выводит дату
сдачи из текущей даты.

Предметная область позволяет проверить факты по фиксированному источнику,
наглядно показать MCP-интеграцию и разобрать реальные ошибки на защите.

## 2. Пользователь и сценарий использования

Пользователь — студент, готовящий учебный проект.

**Свои материалы:**

1. В блоке «Добавить задание» выбрать 1–3 PDF и при желании ввести название.
2. Нажать «Загрузить материалы»; дождаться извлечения текста.
3. Открыть сохранённые PDF, проверить текст и найти нужные фрагменты по запросу.
4. Нажать «Заполнить карточку» в offline или «Разобрать материалы» в live.
   Без модели открывается пустая форма; это не результат AI-анализа.
5. Указать/проверить цель, результат сдачи, требования, критерии и известный срок.
   Подтвердить карточку. Правки помечаются как ввод пользователя, а не факты PDF.
6. Проверить последовательные задачи и минуты, отметить выполненное, задать дни
   и бюджет минут в день. Получить расписание или дефицит времени.
7. Уточнять задание в чате и открывать источники. Без LLM доступны подтверждённая
   карточка и цитаты найденных фрагментов; смысловой ответ модели не имитируется.

Ненужное задание можно удалить. Изменение карточки требует нового подтверждения
и пересчёта; старую версию плана backend отклоняет. Отметки выполненного не
сохраняются между перезагрузками. Если задача требует 300 минут, а доступно 120,
дефицит равен 180. Когда всё выполнено, расписание пустое и остаток равен нулю.

Ограничения: до 10 MiB суммарно, 16 000 извлечённых символов и 100 страниц.
Нужен PDF с текстовым слоем; сканы, пароли и повреждённые файлы отклоняются.
При ошибке одного файла весь комплект не сохраняется. Файлы привязаны к cookie
текущего браузера: после очистки cookie доступ к прежним загрузкам теряется.
Перезапуск сервиса с тем же диском сохраняет задания. AI не имитируется:
новые материалы имеют статус `awaiting_analysis`; после заполнения/разбора —
`needs_confirmation`, после подтверждения — `ready`. Чат и план доступны
только по подтверждённой карточке.

**Подготовленный пример с демонстрационным чатом:**

1. Открыть сайт и выбрать задание.
2. Нажать «Что отправить в LMS?» или написать собственный вопрос.
3. Агент получает описание задания через настоящий MCP-клиент.
4. Ответ содержит две ссылки для сдачи: репозиторий с README/HTML-презентацией
   и работающий сервис. Подтверждение — страница 1 исходного PDF.
5. Открыть выдержку и перейти к нужной странице оригинала.
6. В панели плана указать дни и доступные минуты; получить распределение этапов
   или явное сообщение о нехватке времени.

На вопрос о дате сдачи возвращается уточнение: в исходном задании она не указана.
Три пары сообщений могут храниться в памяти вкладки; при перезагрузке история
очищается. Каждый новый ответ получает свежие MCP-доказательства.

## 4. Архитектурная схема системы

```text
Браузер: HTML / CSS / JavaScript, cookie анонимной сессии
              │ HTTPS → Caddy → внутренняя Docker-сеть
              ▼
FastAPI ──► PDF → ограниченный процесс извлечения → страницы/фрагменты/FTS5
       ├──► SQLite + var/uploads/ (данные своей сессии)
       └──► агент и проверка доказательств
              ├── offline-провайдер (детерминированная демонстрация)
              ├── live-адаптер ──► настроенный Chat Completions API
              └── MCP-клиент
                       │ stdio, отдельный управляемый процесс на запрос
                       ▼
                  MCP-сервер
                       │ чтение
                       ▼
                SQLite / FTS5 / подготовленный пример и свои материалы
```

`studynavigator/catalog.py` создаёт воспроизводимую базу из `data/course.json`,
проверяет SHA-256 исходного PDF и открывает учебные данные для чтения.
`ingestion.py` проверяет PDF и сохраняет комплект атомарно после извлечения;
`sessions.py` определяет доверенную рабочую область браузера.
`mcp_server.py` предоставляет инструменты, `mcp_gateway.py` управляет
подпроцессом и проверкой параметров. `agent.py` ведёт цикл модели;
`providers.py` разделяет offline/live, `planner.py` рассчитывает минуты,
`main.py` обслуживает API и страницы, `web/` содержит интерфейс и HTML-защиту.
`live_budget.py` при явном включении ограничивает расходы по общему журналу.
`cards.py` задаёт общую схему карточки, проверяет источники и нормализует правки.
Карточка и её версия хранятся в SQLite; личный прогресс и диалоги не сохраняются.

У задания есть стабильные ID, требования, критерии, `due_date`/`due_at`,
`source_ids` и типизированные факты. `sources` содержит документ, страницу,
раздел, выдержку и backend URL. Сроки исходного задания равны `null`.
Планировщик текущего среза строит относительный горизонт; дата начала
опциональна, но календарная дата сдачи не придумывается.

## 5. Схема MCP-интеграции

Зафиксирован MCP Python SDK 2.3.0. Сервер запускается как
`python -m studynavigator.mcp_server --db PATH`, клиент использует SDK-протокол
по stdio. На каждый HTTP-запрос создаётся отдельный gateway: вход и выход
соединения происходят в одной async-задаче, trace изолирован от других запросов.
Рабочую область передаёт backend, а не модель. Без неё MCP видит только
публичный подготовленный пример. Чужие задания, источники и документы недоступны.

| Инструмент | Параметры | Результат |
|---|---|---|
| `list_assignments` | Необязательный `course_id` | Список заданий и известные сроки |
| `get_assignment` | `assignment_id` | Требования, критерии, источники и факты |
| `search_materials` | `query`, необязательные `limit` и `assignment_id` | Фрагменты с происхождением; фильтрация выбранным заданием на сервере |

Первым инструментом агента должен быть `get_assignment` выбранного задания.
Для API Яндекса приложение выполняет этот вызов через MCP до первого обращения
к модели, чтобы не оплачивать отдельный выбор уже известного задания;
в trace это отмечено `initiator=application`. Последующий поиск выбирает модель.
Неизвестные имена и неверные аргументы отклоняются до dispatch. Пустой поиск,
неизвестное задание, tool error и сбой транспорта различаются; ошибка не
превращается в успешный ответ об отсутствии заданий. Все инструменты читающие.

Настоящий MCP smoke:

```sh
.venv/bin/python tools/smoke_mcp.py
```

Тест прямой Python-функции не подменяет discovery/call через MCP.

## 6. Описание AI-логики

В live-режиме агент передаёт модели схемы инструментов, исполняет разрешённые
вызовы через MCP и возвращает tool results с соответствующими call ID.
Первая операция закрепляет выбранное задание; последующие вызовы ограничены
его контекстом. Финальный JSON проверяется по схеме.

Разбор карточки сначала получает исходные материалы через MCP, затем вызывает
одну модель с JSON-ответом. Проверяются схема и принадлежность источников.
В запросе анализа к Яндексу источники временно обозначаются `S1…Sn`; ответ
строго переводится обратно в реальные ID, неизвестные обозначения отклоняются.
Это сокращает идентификаторы, но не меняет содержание или границы фрагментов.
Неизменённые сведения из черновика сохраняют происхождение document; исправления
пользователя получают user. Неизвестная дата остаётся null. Подтверждение —
отдельная операция с проверкой версии карточки.

- Идентификаторы источников должны присутствовать в фактически полученных данных.
- Typed facts сверяются с исходными key/value/source_id, включая тип значения.
  Для загруженного задания без канонического списка typed facts модель должна
  вернуть `facts=[]`; смысл ответа всё равно подтверждается источниками.
- При неизвестной дате ответ формируется из `null`-метаданных, чтобы свободный
  текст модели не мог выдать выдуманный срок даже с ошибочным статусом.
- Материалы и история не являются системными инструкциями; их текст не расширяет права.
- Лимиты по умолчанию: 6 tool calls, 45 секунд на запрос, 10 секунд на MCP-call,
  20 секунд на вызов провайдера; на публичном сервере timeout запроса/провайдера
  увеличены до 90/60 секунд. Контекст: 16000 символов исходного примера,
  32000 для карточки загруженного задания с поиском. Исходный текст не дублируется
  в каждой карточке чата; подробности агент получает через search_materials.
- Старая история удаляется раньше источников текущего ответа.
- Отмена HTTP-запроса отменяет обработку и закрывает MCP-процесс.

Проверен OpenAI-совместимый Chat Completions API Yandex AI Studio.
При `LLM_BASE_URL=https://ai.api.cloud.yandex.net/v1` адаптер использует
`Api-Key` и передаёт `OpenAI-Project`, полученный из URI модели
`gpt://<folder_id>/<model>[/<version>]`. Для других API сохраняется Bearer.
В пилоте использованы YandexGPT Pro 5.1 и Alice AI LLM Flash. Необязательный
`LLM_ANALYSIS_MODEL` явно задаёт модель анализа; пустое значение использует
тот же `LLM_MODEL`, что и чат. Автоматического переключения нет. Локальная
конфигурация остаётся offline с выбранной Pro 5.1. Адаптер требует function tools и
`max_tokens`; модели только с Responses API этим адаптером не поддерживаются.
На этапе 5 Flash проверялась через `--model` у live-runner; локальный `.env`
этим не менялся. На публичном сервере этапа 6 настроены `LLM_MODEL` для Pro-чата
и `LLM_ANALYSIS_MODEL` для Flash-анализа с одним общим бюджетом.
Эффективные роли доступны в `/api/status`: `model` и `analysis_model`. Ключ остаётся
на backend в файле вне каталога исходников с правами `0600`.
Для анализа карточки также требуется JSON mode (`response_format=json_object`),
после которого ответ всё равно проверяется Pydantic. Полная Markdown-обёртка
JSON или bare code fence снимается перед разбором; JSON внутри произвольного
текста не извлекается. В chat-запросах с `tools` JSON mode не включается:
[документация Яндекса](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/generation/structured-output)
указывает на несовместимость этих параметров. Формат ответа задаёт prompt,
затем действует строгая валидация. Временный отказ допускает
один повтор в пределах исходного timeout; 401/403 не повторяются. Usage
возвращается, только когда его сообщил API; стоимость и отсутствие usage не выдумываются.

**Offline** — отдельная детерминированная демонстрация на тех же MCP-данных,
без языковой модели и внешних запросов. Режим явно виден в интерфейсе и отчётах.
Для нового задания offline открывает ручную карточку. Если задачи не предложены
моделью, код строит редактируемый список из подтверждённых требований с явно
предварительными оценками 60 минут и завершающей проверкой 30 минут.
Шаблон разработки StudyNavigator применяется только к подготовленному примеру.
Неудачный live-запрос никогда автоматически не заменяется offline-ответом.
Проверка typed facts и ссылок не доказывает истинность каждой фразы живой модели:
для свободного текста нужен отдельный содержательный Eval и разбор ошибок.

## 7. Запуск и развёртывание

### Локальный запуск

Нужны Python 3.12 и `uv`. Команды выполняются из корня проекта:

```sh
uv sync --locked --extra dev
.venv/bin/python -m studynavigator
```

Открыть [локальный сайт](http://127.0.0.1:8000).
База `var/study.db` создаётся автоматически. Переменные `HOST` и `PORT`
меняют bind/порт; по умолчанию используется `127.0.0.1:8000`.
Загруженные исходники хранятся в `var/uploads/`. Путь БД меняет
`STUDYNAV_DB_PATH`, каталог исходников — `STUDYNAV_UPLOADS_PATH` (по умолчанию
`uploads/` рядом с БД). Сохранять нужно и SQLite, и этот каталог.
`var/` исключён из Git. Cookie сессии имеет HttpOnly/SameSite=Lax и Secure на HTTPS;
приватные ответы не кэшируются. Нет аккаунтов и восстановления доступа.

### Подключение модели

Скопировать `.env.example` в `.env`, заполнить `LLM_BASE_URL`, `LLM_MODEL`,
`LLM_API_KEY` и выбрать `STUDYNAV_MODE=live`. Значения секретов не коммитятся.
Каждый разработчик создаёт собственный `.env`; смена ключа требует перезапуска.
URI модели Яндекса должен содержать каталог, доступный этому ключу.
При необходимости отдельного анализа заполнить `LLM_ANALYSIS_MODEL` полным URI;
если поле пустое, обе роли используют `LLM_MODEL`. Это фиксированный выбор,
а не автоматическое переключение при ошибке.
Для запуска с явной загрузкой окружения:

```sh
uv run --locked --extra dev --env-file .env python -m studynavigator
```

Обычная команда `.venv/bin/python -m studynavigator` сама `.env` не читает.
Без обязательной конфигурации live-режим завершается ошибкой при старте.
В `.env.example` ключ пустой, в Git он служит только шаблоном; локальный `.env`
исключён из Git. Сервер не передаёт ключ браузеру.

Пределы ответа задаются `STUDYNAV_CHAT_MAX_TOKENS` (по умолчанию 1000) и
`STUDYNAV_ANALYSIS_MAX_TOKENS` (3000). Timeout провайдера/запроса по умолчанию —
20/45 секунд. Финальная конфигурация сервера — 1000/2200 токенов
и timeout 60/90 секунд; последний диагностический повтор временно ограничивал
чат 400 токенами. Настройки сервера и проверок не меняют default приложения.

Необязательный `STUDYNAV_LIVE_BUDGET_RUB` включает общий денежный предел для
поддерживаемых моделей Яндекса; без него денежного ограничения нет.
`STUDYNAV_LIVE_BUDGET_PATH` задаёт сохраняемый журнал. Перед каждой HTTP-попыткой,
включая повтор, резервируется консервативная сумма; неизвестный расход не
считается нулевым. При нехватке резерва запрос не отправляется. На VPS выставлены
15 ₽ и `/app/var/live-stage6-budget.json`. Это общий бюджет сервиса, а не
ежедневная квота пользователя; перезапуск не обнуляет его. После проверок учтено
13,7011 ₽, остаток 1,2989 ₽. Остатка недостаточно для нового полноценного
Pro-прогона: перед отправкой нужен резерв на весь ограниченный запрос.

## 8. Результаты Eval и разбор ошибок

Подготовлен набор **30 offline-случаев** в `evals/app/cases.json` и воспроизводимый
runner `tools/run_app_eval.py`. Он разделяет реальные HTTP/MCP-сценарии,
детерминированные планы и синтетические проверки защитного контура.
Результат после запуска сохраняется в `var/eval-offline.json`.

Проверяются известные факты, отсутствие ответа, source support, ограничения
плана, сбои инструментов, лимиты и инструкции внутри материалов. Timeout и
пропуски не исключаются из знаменателя. Поля split сохранены, но случаи доступны
разработчику и после отладки не считаются независимой слепой оценкой.

Первый прогон выявил неточности распознавания намерения в offline-провайдере:
баллы конкретного критерия смешивались с общими, длительность защиты — с баллами,
место проведения — с составом слушателей. Исправлено разделение этих признаков
и выбор ответа по фактически полученным данным.

Независимое ревью выявило два обхода защиты даты: финал без получения выбранного
задания и ложная дата в свободном тексте со статусом `insufficient_data`.
Исправлены обязательный контекст задания и каноническая обработка неизвестной даты;
добавлены регрессии. Также исправлена потеря исходной ошибки при cleanup SDK.

Итоги исходного прототипа фиксируются в
[отчёте первого среза](docs/validation/first-slice.md), загрузки —
в [отчёте этапа 1](docs/validation/stage-1.md), карточка и план —
в [отчёте этапов 2–3](docs/validation/stages-2-3.md).
Проверка интерфейса — [отчёт этапа 4](docs/validation/stage-4.md):
**181 Python-тест и 9 JavaScript-тестов прошли**. В Chrome пройден путь
PDF → ручная карточка → план/пересчёт → чат → источник → страница PDF.
Полная проверка только клавиатурой и 360/375 px пока не завершена из-за
ошибок native-автоматизации; точные ограничения перечислены в отчёте.
Эти offline/UI-проверки не являются live Eval. Отдельный ограниченный пилот
этапа 5 действительно обращался к API моделей и сохранил ответы, usage,
MCP-трассы, ошибки и ручные оценки по рубрике:
[отчёт этапа 5](docs/validation/stage-5.md).

Пилот обошёлся в **23,0777 ₽ за 13 генераций** с общим пределом 25 ₽.
После изменений прошли **251 Python-тест, 9 JavaScript-тестов и 30/30
offline-случаев**. Проверка секретов подтвердила, что `.env` игнорируется и не
отслеживается Git, а публичный шаблон не содержит ключа.
Восемь разных случаев охватывают неизвестный срок, факты исходного задания,
разбор оригинального и нового PDF, подтверждение, план, изоляцию и чат.
Не каждый случай требует модели: подтверждение, расчёт и проверки чужой сессии
проверяют обычный код после живого разбора.

Содержательная оценка последних случаев при использовании Pro — **7/8**:
в разборе исходного PDF она опустила явное требование подключённой LLM. Flash отдельно прошла
**1/1** — разбор того же оригинала с полными требованиями и поддержкой источников.
**8/8 получается только при объединении разных моделей и версий.** Это не
единый итоговый E2E-прогон и не статистическая оценка точности. Исправленный
чат использовал настоящие LLM/MCP, но подтверждённая карточка для его повтора
была воспроизведена из предыдущего прогона и не считается новым live-анализом.

Реальные неудачи сохранены: отказ разбора корректного JSON в bare fence,
ссылки у оценочных минут, неполная/неверная привязка критерия к фрагменту,
неканонический typed fact и опущенное обязательное условие. Исправлены parser,
инструкции о происхождении минут/typed facts и короткие обозначения источников;
семантические пропуски не объявлены исправленными одним прохождением схемы.
Исторические неудачи остаются в знаменателе. Цель ≥95% по фактам/источникам
не считается достигнутой по этой малой видимой выборке. Это исторические
результаты этапа 5, а не оценка текущей серверной конфигурации.

На этапе 6 Docker-образ собран на VPS, Caddy выдаёт публичный HTTPS, прошли
**27 основных и 7 дополнительных бесплатных HTTP-проверок**. Полный набор:
**279 Python-тестов за 51,18 с**, **12 JavaScript-тестов** (9 приложения и
3 unit-теста HTML-защиты), 30/30 offline-случаев. Последнее уточнение trusted
контракта отдельно проверено 28 тестами агента. Unit-тесты защиты не являются
проверкой её управления в браузере.
Проверены непубличный backend, непривилегированный процесс, постоянные тома
и отсутствие ключа в image ENV/history/logs. Backup, восстановление в отдельный
том и сохранность данных после реальной перезагрузки VPS подтверждены;
детали — в разделе запуска и [отчёте этапа 6](docs/validation/stage-6.md).

Первый hosted-набор с одной Flash прошёл **5/8** случаев: вопрос о сроке
завершился `unknown_tool`, известные факты и новый чат — `unsupported_fact`.
После явного разделения Pro-чата/Flash-анализа свежий набор прошёл **7/8**;
новый чат снова завершился `unsupported_fact`. Подтверждение, план и изоляция
в этом наборе проверяют обычный код после реального анализа и сами не требуют LLM.
Целевой повтор использовал уже сохранённое реальное задание с исходной cookie,
без воспроизведения БД: после явной передачи `facts=[]` и ограничения чата
400 токенами он завершился HTTP 503 `invalid_model_response`. Raw-ответ не
сохранился, поэтому точная причина последнего сбоя неизвестна.

Затем уточнён системный контракт: пустой `facts` ограничивает одно поле,
полный ответ содержит `answer/status/source_ids/facts`; текст карточки не
попадает в system. Эта последняя правка прошла **28 тестов агента**, включая
сохранённый отказ выдуманному факту. Live-повтор после неё не выполнялся.
Валидация не ослаблялась; ошибочный ответ не превращается в успешный.
Суммарно этап 6 учёл **13,7011 ₽ из 15 ₽ за 14 генераций**, остаток **1,2989 ₽**.
Платные запросы остановлены; резерва на полноценную проверку Pro недостаточно.
Исторические ошибки сохраняются, последний новый чат не принят, цель ≥95%
и завершение этапа 6 не подтверждены. Доказательства и границы проверки —
в [отчёте этапа 6](docs/validation/stage-6.md).
Полная браузерная приёмка, клавиатура и мобильные размеры пока не подтверждены:
Chrome/Safari native-автоматизация возвращает `cgWindowNotFound`, встроенный
браузер недоступен. HTTP-проверки не подменяют эту приёмку.

Подготовка skills оценивалась отдельно: [отчёт о навыках разработки](docs/skills/validation/report.md).
