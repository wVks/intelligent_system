# Проверка качества StudyNavigator

Покажи, какие пользовательские задачи система действительно решает, и сохрани
неудачи для исправления. Прочитай [контекст проекта](../../../docs/project-brief.md),
затем существующий код/тесты и [правила Eval](references/evaluation.md).

Соразмерь объём запросу: для отдельной регрессии достаточно затронутого случая
и связанных проверок. Полный набор, сравнение baseline и отчёт нужны при запросе
полного Eval или изменении основной AI-цепочки; узкая проверка не требует релиза.

## Метод

1. Выбери риск изменения и проверяемый исход. Для фактов используй исходные
   материалы, для ограничений плана — вычисления, для полноты объяснения — явную
   рубрику с примерами. Не оценивай ответ только совпадением слов или JSON-формой.
2. Собери фиксированный набор случаев: известный факт, неизвестные/неоднозначные
   сведения, неверная ссылка, нехватка времени, ошибка инструмента, инструкция
   внутри материала. Разделяй набор доработки и отложенные случаи проверки.
3. Запускай одинаковые случаи в изолированных данных с фиксированной датой/зоной.
   Сохраняй режим, модель/настройки (если использовалась), dataset ID, ответ,
   tool trace и подтверждения оценок. Offline/mock, реальный MCP и live LLM —
   разные уровни доказательств; не смешивай их в общей метрике.
4. Для MCP проверь обнаружение и вызов настоящим клиентом, успешный и ошибочный
   путь, затем транспорт приложения. Тест прямой Python-функции не проверяет MCP.
5. Оцени каждый случай. Ссылка должна подтверждать конкретное утверждение;
   неизвестная дата не должна появляться в ответе; план должен укладываться в
   доступное время. Timeout/отсутствующий ответ входят в знаменатель как неудачи.
6. Сравни с baseline на том же наборе. Для живой модели повтори важные случаи,
   сообщи размер выборки и разброс. Один удачный прогон не доказывает превосходство.
7. Исправь установленную причину, повтори затронутые проверки и нужные регрессии.
   В README запиши реальные ошибки, изменение и итог; не заменяй неудачные
   примеры благополучными после просмотра результата.

## Вспомогательная программа

`scripts/score_eval.py` агрегирует уже проверенные оценки, сверяя их с полным
манифестом случаев. Он не судит правдивость текста и не запускает модель.
Формат и пример — в [references/evaluation.md](references/evaluation.md).
Запуск из корня проекта:

```sh
python3 .agents/skills/study-eval/scripts/score_eval.py DATASET.json RESULTS.json
```

Код 0 — все проверки прошли, 1 — есть неудачи, 2 — неверный формат.
Дубликаты/посторонние ID отклоняются; пропущенные случаи и проверки считаются
неудачами. Оценку `passed` устанавливает проверяющий код или рецензент с
доказательством, а не сама отвечающая модель.

## Результат

Передай воспроизводимые случаи, фактические результаты с режимом, ошибки и
команды повторения. Если приложения или ключа ещё нет, создай нужные fixtures,
offline-проверки и явный статус непроверенного live-сценария; не выдумывай процент.
