Без кода и трассы зависание пока не воспроизведено. Наблюдения указывают на две проверяемые гипотезы: цикл не ограничен и сбой MCP ошибочно преобразуется в пустой список. Исправлять следует эти пути, сохраняя текущий MVP.

1. Зафиксировать два воспроизводимых сценария: fake LLM бесконечно предлагает `search_materials`; затем тот же запрос выполняется при отключённом MCP-сервере. Сохранить длительность, число шагов, тип ошибки и пользовательский ответ без секретов.
2. В backend ввести конфигурируемые общий deadline и предел вызовов инструментов. Проверять оставшийся бюджет перед следующим вызовом. При исчерпании завершать запрос понятным статусом; отменять текущую операцию и закрывать соединение. Повтор не должен запускать новый бесконечный цикл.
3. Убрать преобразование транспортной ошибки в успешное `matches: []`. Пустой успешный поиск означает «совпадений не найдено»; недоступный MCP означает «не удалось получить материалы». Ни один из этих исходов сам по себе не доказывает отсутствие заданий. Не передавать ошибочный результат модели как факт.

Проверки после исправления: ограниченное число вызовов и время завершения; успешный пустой поиск; отключение сервера; timeout; отмена запроса; повторное обращение после ошибки. Регрессии должны падать до исправления.

Нынешний unit-тест Python-функции сохраняем для локальной логики. Добавляем настоящий MCP-клиент: discovery, вызов, ошибка и smoke выбранного транспорта. Отдельно проверяем, что неизвестное имя и неверные аргументы блокируются до dispatch — счётчик клиента равен нулю. Fake LLM проверяет управление циклом; качество подключённой модели этим не подтверждается. Всё перечисленное — план, выполненных тестов здесь нет.
