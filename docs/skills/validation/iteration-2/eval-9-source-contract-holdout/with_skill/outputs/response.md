Минимально выбираем один контракт: `source_ids` плюс каталог `sources` на всех трёх границах. UI перестаёт ожидать отдельное `source_refs`; временный адаптер допустим только в одном месте backend, если нужна совместимость с уже выпущенным UI. Модель не создаёт ссылки и пути.

Пример записи источника:

```json
{"source_id":"project-pdf-p1","title":"Исходный PDF проекта","page":1,"section":null,"excerpt":"В LMS загрузить ссылку на публичный репозиторий с HTML-презентацией и README и ссылку на работающий сервис.","url":"/materials/project-pdf#page=1"}
```

Это проектируемый URL: маршрут `/materials/project-pdf` ещё нужно реализовать для отдачи фактического PDF из серверного реестра. Нельзя считать существование строки доказательством открываемости документа. Backend использует заранее разрешённый ID материала, а не файловый путь или URL от модели.

MCP возвращает факт с `source_ids: ["project-pdf-p1"]` и соответствующий каталог `sources`. Backend проверяет непустые уникальные ID, разрешение каждой ссылки в каталог, страницу от 1, наличие файла и поддержку утверждения выдержкой. В ответе чата утверждение связано с тем же source ID. UI берёт название и URL из каталога и показывает ссылку рядом с конкретным утверждением; пустой URL означает явно недоступный источник, а не пустую активную ссылку.

Приёмка будущей реализации: настоящий MCP-вызов сохраняет ID/страницу/выдержку, API не переименовывает поле, нажатие в UI открывает исходный PDF на странице 1. Отдельно проверяются неизвестный ID, пустой URL и правильный факт с неподходящей выдержкой. Код приложения и эти проверки сейчас не выполнялись.
