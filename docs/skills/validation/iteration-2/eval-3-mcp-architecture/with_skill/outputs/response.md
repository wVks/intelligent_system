Минимальная схема: веб-интерфейс → FastAPI → LLM и MCP-клиент → MCP-сервер → SQLite и исходный PDF. Для одного сервиса выбираю stdio: backend управляет подпроцессом сервера. Отдельный HTTP-сервис сейчас не нужен. Точную версию SDK следует зафиксировать при реализации и сверить её lifecycle с официальной документацией; такой проверки сейчас не выполнялось.

Три читающих инструмента:

- `list_assignments(course_id?)` возвращает краткие задания с ID, названием, сроками и `source_ids`.
- `get_assignment(assignment_id)` возвращает требования, критерии и каталог `sources`.
- `search_materials(query, limit=5)` возвращает фрагменты с ID источника, страницей, выдержкой и URL; предлагаемые пределы: запрос до 500 символов, limit 1–10.

Источники связаны стабильными ID; URL формирует backend для реально обслуживаемого PDF. Неизвестные `due_date` и `due_at` остаются `null`. Аргументы валидируются до доступа к базе, SQL параметризован.

Клиент получает инструменты через discovery, пересекает их с allowlist и передаёт схемы модели. Backend проверяет предложенный вызов и возвращает фактический результат с соответствующим ID. Ключ LLM находится только на сервере. Число шагов, общий timeout и размер контекста ограничены; отмена закрывает ресурсы. Пустой результат, ошибка инструмента и недоступный транспорт различаются.

Доказательство MCP: настоящий клиент выполняет discovery и `call_tool`, сохраняются безопасные request ID, имена, статусы и source ID. Нужны протокольный тест, smoke stdio и интеграция с fake LLM; прямой вызов обработчика этого не доказывает. Для неизвестного имени/неверных аргументов счётчик dispatch должен остаться нулём. Живой LLM-прогон — отдельная последующая проверка. Сейчас ничего не реализовано и не запущено.
