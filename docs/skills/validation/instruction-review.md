# Независимое редакторское ревью project skills

Прочитаны четыре `SKILL.md` и четыре файла `references/*.md`. Outputs испытателей, `cases.json`, авторские expected labels и Eval-примеры skills не читались. Существующие инструкции не изменялись. Это ревью будущего процесса разработки MVP, не проверка приложения или требований PDF.

Критических противоречий не найдено. Полезны две небольшие правки.

## 1. Уточнить единую форму ссылок на источники

`study-build/references/grounding.md:5–10` задаёт для задания `source_refs` и требует доступную пользователю ссылку во фрагменте. `study-mcp/references/contracts.md:11–17,25–27` задаёт `source_ids` в кратком задании, а полное задание описывает только словами; у фрагмента перечислены идентификатор, страница, раздел и выдержка, но способ открыть материал не указан.

`source_refs` и `source_ids` могут законно отличаться для подробного ответа и списка; сейчас их связь не описана. При раздельной разработке MCP и интерфейса это оставляет два разных имени/формата и нерешённый переход от результата инструмента к кликабельному источнику.

Достаточная правка: в `contracts.md` один раз определить полную запись источника и поле подробного задания; явно назвать `source_ids` проекцией этих записей для списка. Указать один механизм открытия материала: поле URL либо маршрут приложения, вычисляемый по `source_id` и странице. В `grounding.md` дать ссылку на это соглашение. Не требуется новый инструмент, сервис или документ со схемами.

## 2. Явно выбирать объём Eval/Release по запросу

`study-eval/SKILL.md:17–33` выглядит как обязательная последовательность полного набора, baseline и правки README для любого применения skill. `study-release/SKILL.md:25–41` безусловно включает чистый запуск, всю цепочку и создание README/HTML-защиты. Это уместно при общей оценке качества/готовности к сдаче, но избыточно для исправления одного критерия Eval или проверки сохранности SQLite после рестарта.

Достаточная правка: одна фраза перед соответствующим списком — для узкого запроса выполнять затронутые шаги и существенные регрессии; полный цикл применять при сравнении версий/оценке общей готовности. Обновлять README и презентацию только когда результат меняет их содержание или они входят в запрос. `study-mcp` уже явно предписывает выбирать проверки по изменению; эту оговорку стоит повторить здесь.

## Что менять не нужно

Повторения правил про `null`, секреты, данные из документов и различие offline/MCP/live оправданы: skills используются независимо, и эти правила защищают реальные границы MVP. Названия `due_date`/`due_at`, лимиты цикла, ошибки MCP и требования к знаменателю Eval согласованы. Новые процессы, обязательные дополнительные артефакты и расширение стека не нужны.
