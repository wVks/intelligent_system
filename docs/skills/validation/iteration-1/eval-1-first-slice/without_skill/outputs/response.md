Первый срез отвечает на один вопрос: «Что отправить в LMS?». Ожидаемый ответ: «Отправьте две ссылки: на публичный репозиторий с README и интерактивной HTML-презентацией, и на работающий сервис. Источник: исходный PDF, стр. 1». Дата сдачи — `null`, потому что в PDF она отсутствует.

Данные: запись `submission` с полями `id`, `title`, `requirements`, `due_at: null`, `source_id: requirements_pdf`, `page: 1`; отдельный материал с дословным фрагментом страницы 1 и именем исходного файла. Страницу нельзя назначать по предположению: при извлечении сохраняем номер из PDF. Для первого среза в SQLite нужны таблицы `assignments` и `materials`, поле происхождения у каждого факта.

Маршрут: HTML-чат → `POST /api/chat` → backend → LLM запрашивает инструмент → MCP-клиент вызывает `search_materials` → MCP-сервер читает SQLite → backend возвращает результат модели → модель формирует ответ с источником → чат показывает текст и ссылку/метку страницы. Достаточно одного фактического запроса поиска; если результата нет или MCP недоступен, ответ сообщает об этом, а не придумывает требования. Ключ LLM остаётся на backend.

Минимум файлов будущего приложения: `app/main.py` (HTTP и чат), `app/llm.py` (API модели и цикл инструментов), `app/mcp_client.py`, `app/mcp_server.py` (три инструмента MVP), `app/data.py` (SQLite и загрузка проверенных фрагментов), `app/static/index.html`, `data/requirements.json`, `requirements.txt`, `.env.example` и `README.md`. Фактический PDF сохраняется отдельно как источник; JSON не заменяет оригинал.

Приёмка: после воспроизводимого запуска пользователь задаёт вопрос и получает обе ссылки как требуемые виды сдаваемых материалов, без придуманных URL; источник указывает на страницу 1, срок отсутствует. В журнале видны реальный обмен MCP и вызов подключённой LLM. При отключённом MCP пользователь видит ошибку получения данных. Сейчас это проект среза; приложение, API и транспорт не запускались.
