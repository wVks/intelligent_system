По описанию есть две проверяемые гипотезы: цикл не ограничен общим бюджетом, а обработчик транспортной ошибки подменяет сбой пустым результатом. Без кода и воспроизведения это ещё не установленная причина. Прямой вызов `search_materials()` не проверяет MCP.

1. Сначала два изолированных воспроизведения. Fake-модель на каждом шаге снова просит поиск; измеряем число вызовов, общее время и закрытие соединения. Во втором запуске отключаем настоящий MCP-сервер/обрываем соединение во время call. Сохраняем request ID, последовательность событий и итог UI без секретов. Отдельный контроль: исправный поиск действительно возвращает `matches: []`. Регрессии должны падать до исправления: превышен бюджет/зависание; транспортный сбой выдаёт «заданий нет».
2. Исправить установленное место завершения loop: общий timeout на весь запрос, предел tool calls/шагов и объёма контекста. Например, первоначально 4 вызова и 30 секунд, конфигурируемо. Каждый повтор расходует бюджет; на исчерпании возвращаем `tool_limit_exceeded`/`timeout`, не запускаем новый цикл. Timeout одного вызова не должен сбрасывать общий дедлайн. Отмена клиента отменяет ожидающий call; cleanup в async context managers/lifespan.
3. Отдельной правкой разделить результат: `ok(matches=[])`, `invalid_arguments`, `unknown_assignment`, `tool_error`, `transport_unavailable`, `timeout`. Не ловить все исключения с возвратом `[]`; проверять `isError` и схему результата. UI: «Не удалось получить задания: источник недоступен. Повторите позже». Модель не получает ошибку как подтверждение отсутствия заданий.
4. Проверить каждый фикс отдельно. Unit: пустой результат сохраняется успешным; `isError`, неверные аргументы и неизвестное имя не становятся фактами. Протокол: настоящий SDK-клиент делает discovery всех трёх инструментов и call; обычная Python-функция недостаточна. Smoke выбранного транспорта с реальным подпроцессом: успешный call, отключение, timeout, закрытие без зависших ресурсов. Интеграция: fake LLM повторяет поиск до лимита, получает фактические tool results с call IDs; ограничение завершается предсказуемо. Проверить UI для успеха, пустоты и недоступности.

Критерий: завершение в заданном общем бюджете с небольшим измеренным допуском окружения, число calls не больше лимита; отключение MCP никогда не даёт уверенного «заданий нет», исправный пустой поиск остаётся пустым. Затем отдельно live LLM, если доступен ключ. Здесь подготовлен план; бага не воспроизводили, код не изменяли, тесты не запускали. MVP остаётся прежним.
