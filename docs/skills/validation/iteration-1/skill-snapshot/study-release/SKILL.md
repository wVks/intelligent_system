# StudyNavigator: выпуск и сдача

Собери проверяемые материалы для защиты работающей системы. Состояние
готовности определяй по выполненным проверкам, а не по наличию файлов.

## Контекст

- Прочитай корневой [AGENTS.md](../../../AGENTS.md) и
  [описание проекта](../../../docs/project-brief.md), затем исходное задание,
  если между ними есть противоречие.
- Для README, рубрики и защиты открой [submission.md](references/submission.md).
- Сохраняй существующий способ запуска и выбранный хостинг, если они пригодны.
  Не создавай дополнительные окружения ради одного учебного сервиса.

## Проверка и подготовка

1. Посмотри реальные команды запуска, конфигурацию, результаты тестов,
   Eval и текущие ссылки. Раздели факты на «проверено», «не проверено»
   и «не выполнено»; укажи основание каждого существенного вывода.
2. Выполни чистый запуск в отдельном временном каталоге либо чистом
   контейнере по инструкции README. Используй lock-файл, если он существует.
   Не удаляй рабочие данные. Проверь создание начальной базы и зависимости.
3. Пройди основной сценарий: интерфейс → LLM → MCP-клиент → MCP-сервер
   → источник → ответ с подтверждением. Отдельно проверь вопрос без данных.
   Сохрани сведения о том, какие части цепочки действительно выполнены.
4. Проверь конфигурацию хостинга: адрес и порт, команду старта,
   переменные окружения, доступ к API модели и состояние базы после рестарта.
   Фиксированную демонстрационную базу можно воспроизводимо создавать при старте;
   изменяемые пользовательские данные требуют постоянного хранения.
5. Если развёртывание входит в запрос и необходимые доступы есть, выполни его
   и проверь публичную ссылку. При отсутствии доступа подготовь конфигурацию
   и перечисли конкретно недостающие сведения. Локальный запуск не доказывает
   доступность сервиса в интернете.
6. Оформи README и интерактивную HTML-презентацию по фактической реализации.
   Проверь открытие презентации и управление ею. Проведи демо по сценарию
   до 10 минут и зафиксируй, был ли хронометраж измерен.
7. Обнови ссылки и статус сдачи; если обнаружена ошибка, исправь в пределах
   задачи и повтори затронутую проверку. Для дефекта основной цепочки подключи
   соответствующий проектный skill, если он доступен.

## Доказательства качества

- Проверяй область результата: успешный mock проверяет лишь моделируемую
  часть, а live Eval — фактический вызов LLM. Не переноси успех одного на другое.
- Публикуй только реально полученные результаты с командой, датой,
  конфигурацией, числом примеров и разбором ошибок. Не назначай себе баллы.
- Ключи храни в окружении; в репозиторий добавляй только пример настроек
  без секретов. Не показывай значения ключей в логах и документации.

## Результат работы

Кратко сообщи, какие файлы изменены и что проверено. Дай фактические ссылки
на репозиторий и сервис либо явно укажи отсутствующие. Перечисли оставшиеся
препятствия к сдаче и способы их устранения. Готовность всех локальных
материалов и готовность публичного сервиса оценивай по отдельным фактам.
