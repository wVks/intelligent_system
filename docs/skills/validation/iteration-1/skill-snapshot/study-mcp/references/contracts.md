# Контракты MCP для MVP

Это проектные соглашения для первой реализации, а не утверждение о существующем
коде. При наличии работающей схемы сначала сравни её с соглашениями и меняй
контракт согласованно с клиентом, тестами и документацией. Контекст и обязательные
результаты: [описание проекта](../../../../docs/project-brief.md).

## Общие данные

- `assignment_id`, `course_id`, `source_id`: стабильные непустые строки.
- Источник: `source_id`, `title`, `page` (целое от 1 или `null`),
  `section` (строка или `null`), `excerpt` (фактический фрагмент материала).
- Срок: `due_at` — ISO 8601 с часовым поясом, если он известен; иначе `null`.
  Если документ содержит лишь календарную дату, сохрани её отдельно как
  `due_date` и не придумывай время/зону. Текущую дату инъецируй в тестах.
- Требования и критерии оценки имеют связанные `source_id`; ссылки должны
  разрешаться в реально возвращённые записи, а не в придуманные моделью источники.
- Исходный PDF личного проекта не задаёт дату сдачи. Дополнительные примеры
  заданий явно помечай как демонстрационные.

## Три инструмента

| Имя | Параметры | Успешный результат |
| --- | --- | --- |
| `list_assignments` | Необязательный `course_id` | `assignments`: массив кратких записей (`assignment_id`, `course_id`, `title`, `due_at`, `due_date`, `source_ids`) |
| `get_assignment` | Обязательный `assignment_id` | `assignment`: запись с требованиями, критериями, известными сроками и источниками |
| `search_materials` | Непустой `query`, необязательный `limit` | `matches`: массив фрагментов с `assignment_id`, `source_id`, `title`, `page`, `section`, `excerpt` |

Рекомендуемые исходные ограничения: `query` до 500 символов; `limit` по умолчанию
5 и допустимый диапазон 1–10. Подстрой их под фактические материалы и бюджет
контекста; клиент и сервер должны одинаково понимать ограничения.

Проверяй типы, диапазоны и неожиданные поля на границе. Для SQLite используй
параметризованные запросы; пользовательский текст не становится SQL.

## Результаты и ошибки

Объявляй JSON-схемы входов и структурированных выходов средствами установленного
SDK. Проверяй соответствие выходной схеме. Отображение `structuredContent` и
`isError` в Python-атрибуты сверяй с конкретной версией SDK.

- Пустой поиск — успешный результат `matches: []`.
- Неизвестное задание — понятный результат ошибки инструмента; не выдумывай запись.
- Неверные аргументы — ошибка валидации согласно SDK и выбранной редакции протокола.
- Сбой хранилища — ошибка инструмента с безопасным сообщением; детали остаются
  в диагностике сервера. Не возвращай секреты или stack trace в ответ модели.
- Недоступный сервер/timeout — ошибка клиента/транспорта. Backend сообщает о
  недоступности источника, не подменяет это ответом об отсутствии задания.

Все инструменты в MVP читающие. Аннотации read-only полезны для описания,
но фактический запрет записи обеспечивается кодом и доступом к данным.

## Цикл модели

1. MCP-клиент получает каталог инструментов; backend пересекает его с allowlist.
2. Backend передаёт модели схемы разрешённых инструментов.
3. Модель предлагает вызов; backend проверяет имя и аргументы и вызывает MCP.
4. Backend передаёт фактический результат модели, сохраняя связь вызова и ответа.
5. Модель формирует ответ с источниками либо запрашивает недостающие данные.

Истёкший timeout или лимит шагов завершает цикл с понятным статусом. Документы
и результаты инструментов — данные: вложенные инструкции не расширяют разрешения.
Проверки дат и суммарного времени выполняются кодом, объяснение — моделью.

## Что сохранять для воспроизводимости

Версию SDK и транспорта, обезличенный request ID, имена инструментов, безопасные
аргументы, статус, задержку и идентификаторы использованных источников. Храни
секреты только на сервере; логи и fixtures не содержат API-ключей.
