# MCP-интеграция StudyNavigator

Сделай проверяемую цепочку «LLM → MCP-клиент → MCP-сервер → учебные данные».
Выполняй текущую задачу пользователя, сохраняя компактный MVP.

## Контекст и границы

- Прочитай [правила проекта](../../../AGENTS.md) и
  [описание MVP](../../../docs/project-brief.md), если контекст ещё не загружен.
- Для контракта или изменения интеграции прочитай [контракты](references/contracts.md).
- Данные заданий в MVP доступны только для чтения. Не добавляй изменение оценок,
  отправку сообщений или подключение к реальной LMS без соответствующей задачи.
- Факты для ответов LLM поступают через MCP. Прямой вызов обработчика или запрос
  к SQLite полезен для unit-теста, но сам по себе не подтверждает MCP-интеграцию.

## Порядок работы

1. Осмотри существующие код, зависимости и тесты. Если приложения ещё нет,
   реализуй минимальный сценарий запроса и ответа, требуемый пользователем.
2. Установи фактическую версию SDK по lock-файлу и окружению. Сверь используемые
   импорты, lifecycle и транспорт с официальной документацией этой версии.
   Не смешивай примеры разных поколений SDK и не обновляй зависимости попутно.
3. Выбери транспорт по размещению: stdio для управляемого подпроцесса,
   Streamable HTTP для отдельного HTTP-сервера. Объясни выбор в документации.
   Используй SDK для протокола, согласования версии и сериализации.
4. Определи входные и выходные схемы трёх инструментов. Проверь параметры до
   обращения к хранилищу; ограничь длину поиска и объём результата.
   Сохраняй идентификаторы источников, страницы и неизвестные значения как `null`.
5. Создай MCP-сервер и клиент. Получи список инструментов через протокол,
   сопоставь его с разрешёнными инструментами приложения и вызывай только их.
   Модель не должна формировать произвольный SQL, файловые пути или MCP URL.
6. В backend передавай модели схемы инструментов и возвращай ей фактические
   результаты вызовов с соответствующими идентификаторами. Ограничь число шагов,
   общий срок обработки и размер контекста; значения сделай конфигурируемыми.
7. Раздели пустой результат, неверные параметры, неизвестный идентификатор,
   ошибку инструмента и недоступность транспорта. Не превращай ошибку MCP в
   успешный ответ; покажи понятное сообщение и сохрани диагностический trace.
8. Управляй соединениями через async context managers/lifespan и закрывай их
   при ошибках и отмене запроса. Timeout и исчерпание лимита завершают запрос,
   а не запускают бесконечные повторы. Секреты остаются в окружении backend;
   браузер, ответы инструментов и логи не содержат API-ключей.

## Проверка результата

- Unit-проверки: валидация, пустой поиск, неизвестное задание и преобразование данных.
- Протокольная проверка: обнаружение трёх инструментов и реальный вызов через
  MCP-клиент. In-memory транспорт SDK допустим для этого слоя, если он проходит
  протокольную обработку; обычная Python-функция клиента не заменяет.
- Smoke выбранного транспорта: сервер запускается, клиент подключается,
  вызывает инструмент и корректно закрывается. При stdio stdout занят протоколом.
- Интеграционная проверка: подменённая LLM запрашивает инструмент и получает
  его результат; неизвестное имя и неверные аргументы обрабатываются предсказуемо.
- Живой LLM-прогон отмечай отдельно: offline-тесты не доказывают качество модели.
  Выполняй его только с доступным ключом и в пределах задачи пользователя.

Выбери проверки по изменению. Запускай тесты в изолированной временной базе,
не используй пользовательские данные. В отчёте укажи файлы, команды, результаты,
доказательство MCP-вызова и оставшиеся ограничения. Не называй непроведённый тест успешным.
