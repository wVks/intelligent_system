Честный итог по предоставленным числам: **24/30 = 80% успешных случаев**, 6/30 = 20% неуспехов: 4 timeout (13,33%) и 2 отсутствующих результата (6,67%). Знаменатель — все 30 заранее назначенных случаев. «24/24 = 100% среди полученных ответов» — условная доля, скрывающая отказы, и не общая оценка качества.

Режим — `offline`, провайдер fake. Даже 80% означает лишь успех по критериям этого offline-прогона, если метки 24 случаев действительно проверены; исходные ответы, рубрика и trace нам не предоставлены. Нельзя приписывать результат подключённой LLM, настоящему MCP или сервису на хостинге. Семантическая достоверность и качество ссылок отдельно не доказаны. Распределение критичных ошибок по исходным ID неизвестно.

В `counts.json` сохранены только сообщённые агрегаты. `aggregate_counts.py` воспроизводит арифметику и проверяет, что сумма равна 30; `arithmetic-result.json` — вывод этой команды, не повторный прогон приложения. Подробные case IDs и оценки не выдуманы. Агрегатор study-eval требует полного манифеста и уже проверенных оценок: без них его запуск не восстанавливает исходный Eval.

Для повторения настоящего прогона нужны: те же 30 case IDs/запросов и fixtures, ожидаемые checks до запуска, версия приложения и материалов, конфигурация fake-провайдера и фиксированные дата/зона, лимиты шагов/timeout и число повторений. Изолировать SQLite; запустить все 30 без удаления неудач. Для каждого сохранить сырой ответ, trace, status/error, задержку и доказательства каждого `passed`; отсутствующие ответы явно зарегистрировать. После этого агрегировать по полному манифесту. Команду приложения пока назвать нельзя: код и runner не представлены.

Для диагностики разобрать четыре timeout по trace (транспорт, provider или tool loop), а два отсутствующих результата — по жизненному циклу запроса/сохранения. До trace причины не установлены. Исправить найденную причину и повторить те же случаи; первоначальные ошибки сохранить. Отдельными прогонами проверить протокольные discovery/call, выбранный транспорт, live LLM и hosted-сценарий. Сравнивать версии на одном наборе и конфигурации; для live повторить важные случаи и указать разброс.
