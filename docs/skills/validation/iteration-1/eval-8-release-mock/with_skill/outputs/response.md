Фразу «MCP работает стабильно, сервис готов к защите» пока публиковать нельзя: представленные проверки этого не доказывают. Достоверная формулировка подготовлена в `README-status.md`, проверки — в `pre-submission-checks.md`.

По условию подтверждены только зелёные offline-тесты с mock HTTP/LLM, прямые вызовы Python-функций, ответ `/health` и пересоздание SQLite после рестарта. Я сам эти действия не повторял: URL, код и результаты не предоставлены, сеть запрещена. Mock проверяет смоделированные компоненты; прямые функции — обработчики, но не MCP. `/health` показывает доступность одного endpoint, а не пользовательского пути с LLM и источниками. Live-чат, полный MCP-обмен и воспроизводимость данных пока не проверены; готовность к защите не подтверждена.

Проверки перед сдачей, в порядке зависимости:

1. Зафиксировать commit/lock, SDK, модель и настройки окружения без значений ключей. В чистой среде выполнить реальные команды README; сохранить команды/exit codes и подготовку SQLite.
2. Настоящим MCP-клиентом выполнить initialize/discovery всех трёх разрешённых инструментов и call. Проверить валидный/пустой поиск, неверные аргументы, неизвестный ID, tool error, timeout/недоступность. Затем smoke именно транспорта приложения и корректное закрытие; stdout stdio оставить протоколу. Сохранить trace без секретов.
3. С доступным ключом запустить live-цепочку «веб-чат → LLM → MCP → PDF → ответ»: две ссылки для LMS и опора на стр. 1; неизвестная дата остаётся null; инструкция внутри материала игнорируется. Сбой MCP не превращается в «заданий нет», повторный поиск ограничен бюджетом.
4. Повторить те же действия через публичный URL, затем после рестарта. Проверять схему/источники/ID и фактический ответ, а не только `/health`.
5. Установить назначение SQLite. Если это неизменяемый демонстрационный seed, пересоздание допустимо при воспроизводимых данных и явном ограничении. Если в базе сохраняются изменяемые пользовательские данные — их потеря является дефектом: настроить постоянный volume/хранилище и проверить сохранность тестовой записи в изолированной среде. Не уничтожать рабочие данные.
6. Провести Eval: полный манифест, raw answers/trace, timeout/пропуски в знаменателе; отдельно offline, MCP, live, hosted. Записать реальные ошибки/исправления в README, проверить публичный репозиторий/ссылки и интерактивную HTML-защиту с измеренным временем ≤10 минут.

PDF требует работающий сервис, MCP, подключённую LLM, Eval/разбор ошибок, README и HTML; для LMS — ссылки на публичные репозиторий и сервис. В этой работе создан отчёт и план проверок, тесты приложения не выполнялись.
