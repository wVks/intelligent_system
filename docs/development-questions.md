# StudyNavigator: вопросы для дальнейшей разработки

**Назначение:** собрать решения, которые помогут последовательно довести проект
от описания до работающего сервиса и защиты. Документ содержит **160 вопросов**,
сгруппированных по этапам и областям ответственности.

Контекст: [описание проекта](../README.md), [границы MVP](project-brief.md),
[исходное задание](../Личный%20проект.pdf).

## Как пользоваться

Начать стоит с десяти вопросов **START**. Они уточняют реальные ограничения
пользователя. Остальные вопросы решаются при работе над соответствующим этапом.
Первый сценарий по имеющемуся PDF можно разрабатывать параллельно с уточнениями;
отсутствие доступа к модели ограничивает live-проверку, но позволяет подготовить
данные, настоящий MCP и offline-проверки.

Приоритеты:

- **P0** — уточнить в первую очередь: сроки, доступные данные, доступы и бюджет.
- **P1** — решить при реализации соответствующей функции или перед публикацией.
- **P2** — рассматривать после подтверждения полезности MVP.

Ответственные:

- **Пользователь** — цель, ограничения курса, доступность аккаунтов и расходов.
- **Разработчик** — технический выбор и проверка его работоспособности.
- **Совместно** — поведение продукта, критерии качества и компромиссы.
- **Преподаватель/эксперт** — подтверждение учебных требований и согласование темы.

Отметка `[x]` означает, что ответ записан и понятен способ его проверки.
Неизвестный ответ можно оформить как допущение с датой пересмотра. Для важных
решений используйте запись:

```text
ID вопроса:
Ответ / принятое решение:
Статус: подтверждено / допущение / требует проверки / отложено
Основание: источник, наблюдение или результат проверки
Ответственный:
Как проверим:
Когда пересмотрим:
```

Поскольку репозиторий предназначен для публикации, ответы о доступах должны
содержать только статус и способ настройки. Значения API-ключей, пароли,
приватные SSH-ключи и персональные данные студентов сюда не записываются.

## Что уже выбрано

Следующие решения составляют исходную основу и пересматриваются при появлении
конкретной причины:

- Один курс, заранее подготовленные материалы, первый источник — имеющийся PDF.
- Веб-чат и список заданий; Python/FastAPI, SQLite, HTML/CSS/JavaScript.
- Один AI-агент с LLM по API и собственные MCP-клиент и сервер.
- Три читающих инструмента: `list_assignments`, `get_assignment`, `search_materials`.
- Начальная MCP-схема — управляемый процесс и `stdio` внутри одного размещения.
- Источники у фактов; неизвестные `due_date` и `due_at` остаются `null`.
- Даты, суммы часов и ограничения плана проверяются кодом.
- Первая версия охватывает подготовленные материалы; реальные LMS, аккаунты,
  уведомления, календарные интеграции и произвольные загрузки PDF отложены.

Провайдер модели, хостинг, сроки и согласование темы пока не подтверждены.
Приложение ещё предстоит реализовать; результаты испытаний skills относятся
к подготовке разработки, а не к качеству будущего сервиса.

## Как превратить ответы в следующий рабочий этап

| Этап | Какие ответы нужны | Проверяемый результат |
|---|---|---|
| 1. Подготовка | START и минимальные DATA/SEARCH | Подготовленный PDF, записи задания, подтверждённые выдержки и воспроизводимые seed-данные |
| 2. Первый сквозной срез | MCP, нужные APP/MODEL, первый эталон EVAL | Запрос про LMS проходит через настоящий MCP; live LLM проверяется при доступном API; источник открывается |
| 3. Полезный MVP | ANSWER, PLAN и UX по реализуемым сценариям | Требования объясняются с источниками; неизвестное уточняется; план проверяется по ограничениям |
| 4. Доказательство качества | EVAL и соответствующие негативные MCP/APP | Сохранённый прогон с полным знаменателем, трассами, ошибками и повторной проверкой исправлений |
| 5. Публикация и защита | OPS и DEMO | Публичная рабочая цепочка, воспроизводимый README, интерактивная HTML-защита и две ссылки для LMS |
| 6. Развитие | NEXT и наблюдения реальных пользователей | Выбранное расширение с основанием, границами и измеримым критерием успеха |

Первый набор эталонных запросов уже можно зафиксировать по имеющемуся PDF:

1. «Что отправить в LMS?» — две ссылки, источник на странице 1.
2. «Сколько баллов дают за MCP?» — максимум 10, источник на странице 2.
3. «Когда сдавать?» — дата отсутствует, нужно уточнение.

После ответов START фиксируем реальные ограничения, выбираем ближайший
проверяемый результат и создаём короткие задачи первого среза. Остальные вопросы
становятся частью соответствующих задач, а ответы с подтверждениями постепенно
обновляют README и проектный контекст.
